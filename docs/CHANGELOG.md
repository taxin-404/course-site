# Changelog

## Unreleased
### Added (course banners, resource editing and the 3/2/1 grid)
- **A home-screen course card can now carry an image banner.** Drop `banner.jpg`, `banner.jpeg`, `banner.png` or `banner.webp` into a course's top-level folder through **Admin panel → Files** and the card shows it full-width at a 16:9 centre crop above the title; a course without one keeps the old card exactly. There is no schema change and no pointer: the banner is an ordinary R2 object, so Upload / **Replace** / Delete work as for any file, and the course tree filters it out of the lesson list. When several extensions exist at once, `worker/banners.js` picks jpg, then jpeg, then png, then webp. `GET /api/banner/<course>` serves the bytes to any **signed-in** user, enrolled or not, so a locked course's card still shows its banner; the opened course page is unchanged. The file manager labels the row **· course banner**, draws a picture icon for images, and shows a course-folder hint.
- **A lesson resource can now be edited instead of deleted and re-added.** The Resources tab on a video/YouTube lesson shows a pencil beside the trash; the dialog edits the title and note, plus the link URL for a link, and saves in place (a link keeps its id). A PDF is title and note only — its file is `file_key` and is never replaced by an edit; replacing a PDF is still delete + upload. `PATCH /api/admin/resources/<id>` enforces the lesson's admin access, validates an `http(s)` link, and ignores a submitted `url` for a PDF, so the stored file key cannot be overwritten.
- **The home grid is now three course cards per row on a wide screen, two when narrower, one on phones.** The grid minimum dropped from 460 px to 340 px (`minmax(340px, 1fr)`); the existing `max-width: 760px` single-column rule still applies, so a 1280 px viewport shows three ~394 px cards, 900 px shows two, and 390/320 px show one with no horizontal overflow.
- **Verified:** `npm test` 66/66, `npm run typecheck`, `npm run build`, `npm run check:scripts`, then deployed to dev and checked live. A throwaway course named `Banner Test & Co` (space and `&`) uploaded, replaced and deleted its banner entirely through the file manager; the card picked up the new bytes immediately with `cache-control: private, no-store`; `banner.png` did not beat `banner.jpg`; deleting both made `/api/banner/...` answer `404` and removed the card image. A throwaway student saw the locked course's banner while its CTA read **No access**, and an enrolled course without a banner showed none. The grid measured 3 / 2 / 1 columns at 1280 / 900 / 390 px (and no overflow at 320 px), in both themes. A link resource kept id 3 while title, URL and note changed; a PDF kept its `file_key` through the dialog and through a crafted PATCH carrying a `url`, and still opened afterwards. All test resources, the throwaway course and the student were deleted, and dev was left as found.

### Hardened (a stalled database query can no longer hang a screen)
- **Every D1 query is now raced against an 8-second deadline, so a stalled call answers `503` instead of pinning the request.** The schema gate already had a deadline, but every query *after* it — a session lookup, the course tree, a progress write — was a plain D1 call with no timeout of its own. One stalled call left the request in flight forever: the Worker logged nothing, and the client (which had no timeout either) sat on a blank screen until a reload. `guardDb`/`guardEnv` now wrap the request's `DB` binding so `prepare().bind(...).first()/all()/run()/raw()` and `batch` all resolve through the same deadline; a timeout maps to the existing `503` + `Retry-After: 5`. The wrapper is transparent — it unwraps guarded statements before `batch`, so workerd still receives real `D1PreparedStatement`s — and it never touches `/api/config`, which stays DB-free. On the client, `Api.req` aborts a JSON call after 20 s and reports it as a failed call, so bootstrap lands on the sign-in screen instead of a blank one. Verified with `npm test` 56/56 (5 new: a stalled query rejects at the deadline, the deadline survives `bind()`, `batch` receives the original statements, real query/batch results pass through, and `guardEnv` routes only `DB` through the guard) plus `typecheck`, `build`, `check:scripts`.

### Fixed (Google sign-in nonce)
- **"Google sign-in failed" no longer happens because the nonce went stale.** The client cached the `/api/config` response for the whole SPA lifetime and the server rotated the nonce (and overwrote the single `gn` cookie) on every call, so a page left open past the cookie's 12-hour life — or an SPA page reached after a logout, or a second tab — presented a nonce that no longer matched the cookie and the callback was rejected with `401`. The login form now fetches a **fresh** config when it mounts (`Api.freshGoogleConfig`), and `/api/config` **reuses** the nonce the browser already holds instead of rotating it, so two tabs and a long-lived page agree. The value is still unguessable and HttpOnly, so replay stays bound to the browser. Verified with a new `worker/security.test.mjs` test (a second call with the cookie returns the same nonce; a junk cookie is replaced, never reflected) — `npm test` 51/51, `typecheck`, `build`.

### Fixed (database stalls / outage)
- **One stalled D1 call no longer takes the whole site down until the next deploy.** `ensureSchema` memoised a promise in module scope and every API route awaited it. D1 binding calls have no per-call timeout, so when one call stalled the promise never settled; every later request reused it and hung too — observed as 10–60 s client timeouts with `cpuTime: 0` / `outcome: "canceled"`, while requests that returned before any DB access still answered in ~30 ms. The schema promise is now raced against an 8 s deadline; on timeout the cache is dropped and the request gets `503 {"error":"Database temporarily unavailable"}` with `Retry-After: 5`, so the next request retries the (idempotent) schema statements instead of inheriting the dead promise. The five `pragma_table_info` checks are also one batched round trip now. Verified with 4 new `worker/schema.test.mjs` tests (config is DB-free, a never-settling call rejects at the deadline, a timeout maps to `503` + `Retry-After`, the next call rebuilds the schema) — `npm test` 50/50, `typecheck`, `check:scripts` — plus a live dev pass (config 21–32 ms warm, login `200`, `/api/me` `200`, `/api/course` `200`).
- **`/api/config` no longer touches the database.** It only reads `GOOGLE_CLIENT_ID` and mints the sign-in nonce, but it sat behind `ensureSchema`, so during a DB stall the sign-in screen could not render at all. It is now handled before the schema gate.
- **The dev database now lives in APAC instead of WNAM.** `wrangler d1 info` reported `running_in_region: WNAM` while the Worker runs in Dhaka, so every D1 round trip crossed the Pacific (~293 ms measured from a probe Worker, and ~3.1 s for a cold schema pass of ~10 sequential calls). The dev DB was exported, recreated as `course-db-apac` (`--location=apac`) and imported; the same probe now measures ~83 ms per round trip and a cold schema pass is ~1.1 s. Data was verified after the move (4 users, notes + note image, enrollments) with a live login and course load. The old `course-db` is kept as a fallback.
- **Production recovered by redeploying the unchanged `main` commit.** Both sites were stuck in the same way at once; a throwaway probe Worker with the same prod database returned in ~815 ms (`SELECT 1` 293 ms), proving D1 itself was healthy and only the long-lived `course-site` isolates were poisoned. `npm run deploy` from `main` (commit `458f49c`, no code change) restored it: first request 3.09 s, then 23–40 ms.
- **Production then got the full fix and the APAC database.** `dev` was merged to `main` and deployed, and the prod database was recreated the same way (`course-db-apac`, 553 kB, in region APAC). The prod export overflowed D1's ~100 KB per-statement limit on three `pdf_notes` rows (one 295 KB, from before the R2 image move), so the short statements were imported with `wrangler d1 execute --file` and those three through the D1 API with bound parameters. Verification: every table's row count matches the old database, including the 378,959 bytes of PDF notes; `/api/config` answers in 31–52 ms; a wrong-password login is a fast `401` in ~1.15 s; and the `attempts` rows that login created appear in `course-db-apac` and not in the WNAM `course-db`, which is kept as a fallback.

### Fixed (PDF images)
- **Adding an image to a PDF now saves and reloads.** PDF.js serializes a pasted image (stamp) as a full-resolution base64 PNG data URL in the note's `bitmapUrl`, which broke in two ways: (1) on reload the viewer re-adds the note with `addEditorAnnotation`, and PDF.js loads the picture with `fetch(bitmapUrl)` — fetching a `data:` URL is blocked by the page CSP (`connect-src` has no `data:`), so a saved image silently vanished; (2) the inlined base64 is ~4/3 the image size, so a large image pushed the notes JSON past the 1.5 MB endpoint cap (`413`) and nothing was stored — and that cap cannot be raised, because D1 hard-caps a row at 2 MB. Now each image is uploaded once to R2 under a private per-student, content-addressed key (`_notes/<user>/<sha256>`), and the note keeps the short same-origin URL (`PUT/GET /api/note-asset/<lesson>/<id>`); the browser decodes the data URL itself (no CSP-blocked `fetch`), hashes it with SHA-256 for the id, and caches the URL so editing does not re-upload megabytes. This fixes both symptoms at any image size and keeps the notes row small. The route mirrors the notes rules (signed-in user + granted course), accepts only PDF.js's image types (SVG is sandboxed), caps one image at 16 MB and 500 images per account, serves the bytes `private, immutable`, and the assets are pruned when their notes are saved/cleared, the lesson is deleted, or the user is deleted. The reserved `_notes` prefix is hidden from the course list and the admin file manager. Verified with 6 new `worker/security.test.mjs` tests (round-trip + owner isolation + type/size/id validation, cross-course `403`, prune-on-save and delete-on-clear, a hidden `_notes` prefix, user delete and lesson delete) — `npm test` 46/46 — plus `typecheck`, `build` and `check:scripts`.

### Fixed (PDF notes appear faster)
- **Notes no longer wait for the whole PDF to load before their request even starts.** `onLoaded` is triggered by the reader's `pagesLoaded` event, so the notes were fetched only after the document had fully loaded; the server round trip (~1.2 s on dev, where each D1 query is slow) then ran on the critical path, and a pasted image waited on it too. The viewer now kicks off the notes request at component init (`ngOnInit` → `loadNotes`) and shares one promise with `onLoaded`, so the fetch overlaps the PDF download and the notes are ready when the pages render. Measured on dev: the notes request used to start ~3.1 s in and appear ~6.5 s / ~4.5 s (cold/warm image); it now starts ~1.3 s in and the notes appear with the page (~5.0 s / ~3.4 s), the remaining time being the PDF page render itself. `npm test` 46/46, `typecheck`, `build`.

### Hardened (PDF downloads)
- **A PDF can no longer be dumped at wire speed in one request.** Videos are already served only to byte-range requests, so a plain `GET` is refused and bulk downloading needs hundreds of capped, speed-limited requests. A PDF cannot use that rule: PDF.js opens every PDF with one plain `GET` (it only switches to byte ranges for files larger than twice its chunk size, and a downloader's `GET` is identical to the viewer's), so refusing or chunk-capping the request breaks the viewer. Instead the response **body is paced**: each student has a token bucket (`worker/limits.js` `pace`, used by `paceBody` in `worker/index.js`) and every PDF byte flows through it at `MAX_PDF_MBPS` (default: `MAX_MBPS`, 12 Mbit/s) with a 5-second burst, so the first pages still paint but a whole file — or a script — cannot finish instantly. Admins are exempt. Verified with new `worker/security.test.mjs` tests (the pure pacer allows a burst then charges the rest at the rate; a 520 KB body at 0.8 Mbps provably waits ≥150 ms and arrives intact) — `npm test` 40/40, plus `typecheck` and `build`.

### Added (single-device login)
- **A student account can now be signed in on only one device at a time.** The Worker stores one `sid` (session id) per user: every login writes a fresh random `sid` and puts it in the signed cookie, and `getUser` rejects a non-admin cookie whose `sid` no longer matches the row, so signing in on a new device immediately signs the old one out. Admins (and the owner) are exempt and keep working across devices. On deploy every existing student cookie (which has no `sid`) is rejected once — a one-time sign-out of current students. On the client, any `401` clears the local session back to the sign-in screen, and a `window focus` / `visibilitychange` handler re-checks the session so a device that is idle on the course list notices it was displaced. Verified with a live Worker pass (the second student login `401`s the first, the legacy pre-change cookie `401`s, two admin logins both stay `200`) and a headless Chromium check (the displaced device returns to sign-in on refocus; a network failure does not sign a live device out).

### Fixed (file manager)
- **Deleting a folder failed with `D1_ERROR: LIKE or GLOB pattern too complex`.** The row cleanup matched `content_order` and `youtube_lessons` prefixes with `path LIKE ? ESCAPE '\'`, and D1's `batch()` endpoint rejects an escaped LIKE pattern even though the identical statement runs fine on its own. The files were already removed first, so the folder was left half-deleted ("The files are gone…"). The prefix is now an exact range (`p/ <= path < p0`) built from plain comparisons, which `batch()` accepts. Verified by creating and deleting a throwaway folder with a nested position row and a YouTube row: `{"ok":true,"deleted":1}` and both rows cleaned.
- **Renaming a section with a long (or unicode) name failed with a generic "Server error".** `moveEntry` matched a folder's YouTube-lesson rows with an escaped `LIKE`. D1 rejects any LIKE pattern whose literal prefix passes ~50 characters with `LIKE or GLOB pattern too complex` — a section path (parent + name, especially with a multi-byte emoji) crosses that easily while a short top-level course name does not, so the same rename worked or failed by length alone. The three prefix matches (the subtree SELECT and the source/destination YouTube counts) are now plain ranges (`from/ <= id < from0`), the idiom the delete path already uses. Verified by renaming `zz-rn-parent/🟢 Computer Peripherals Live Class` → `…/🟢Computer…`: `Server error` before, `{"ok":true,"moved":1}` after, with the section's YouTube lesson carried to the new id.

### Fixed (PDF viewer)
- **Saved notes were not shown when a PDF was reopened.** `pagesLoaded` fires before PDF.js renders the annotation editor layer, and `addEditorAnnotation` silently skips notes when that layer does not exist. The viewer now restores each page's notes after that page's `annotationEditorLayerRendered` event (so notes on later pages restore on scroll), merges not-yet-rendered saved notes into every save so an edit cannot delete them, and uses a fresh viewer instance per PDF id so switching lessons cannot reuse another document's note state. Affects PDF lessons and resource PDFs.

### Added (players)
- **Picture-in-picture works on self-hosted lessons** (HLS and MP4): the skin's own PiP button enters and exits it, and playback keeps its position. YouTube lessons report PiP as unsupported (the adapter cannot hand an iframe to the browser), so the feature is self-hosted only.
- **Subtitles from tracks already embedded in the source video.** `tools/make-hls.sh` probes each source with `ffprobe` and converts every text subtitle track to WebVTT next to the playlist as `index.<lang>[.<n>].vtt` (`<lang>` lowercased from the stream tag, `und` when absent; duplicate languages get `.2`, `.3`). Extraction runs **before** the "already encoded" skip, so re-running the encoder on an existing lesson adds the `.vtt` files without re-encoding the video; the video encode now passes `-sn` so ffmpeg does not also write stray `index0.vtt` / `index_vtt.m3u8`. Bitmap subtitles (PGS/VobSub) are skipped.
- The Worker serves `.vtt` as `text/vtt` on the same protected `/api/media/*` route, attaches each folder's tracks to its `index.m3u8` lesson as `subtitles: [{ key, lang }]`, hides `.vtt` in the admin file list like `.ts`, and counts a lesson's subtitles as the same lesson in the per-user scrape cap.
- The app renders one `<track kind="subtitles">` per entry inside `<hlsjs-video>` / `<video>`, labelled with `Intl.DisplayNames` (`English`, `English (2)` for duplicates, `Undetermined` for `und`). **Captions are off by default**; the viewer turns them on from the skin's captions button (desktop) or Settings → Captions (phones, where the button is hidden below 512px). No new upload UI, no transcription, no cost.
- Verified in a real browser (local Worker + seeded HLS fixtures): tracks load with every `mode` `disabled`; selecting `English` paints the `Hello` cue over the video with the watermark and single control bar; `English (2)` and `Undetermined` are selectable; an HLS lesson with no `.vtt` shows no captions button and plays unchanged; at 390×844 the settings menu still lists and selects the track. Layout matrix 1920×950 / 1440×900 / 1366×768 / 900×800 / 390×844: no horizontal overflow, two columns at ≥1100px, single column below, player fits the viewport, no cue/watermark overlap.
- Bundles after this change: initial JS transfer **66.51 kB** (unchanged); `player` 640.87 kB raw / 162.97 kB transfer (was 640.00 / 162.81); `yt-player` 15.52 kB / 5.39 kB. `main-*.js` still contains no Video.js or hls.js code (`grep` count 0); its gzip moved 10001 → 10002 bytes only because it embeds the renamed lazy `course` chunk.
- **No resolution selector** and **no encoder quality change**: YouTube's IFrame API no longer lets a third-party embed set playback quality (`setPlaybackQuality` is a no-op, `setPlaybackQualityRange` is gone and the setters are no longer documented), and the only working quality menu is YouTube's own chrome, which this player deliberately hides. Self-hosted lessons stay a single full-resolution HLS rendition encoded with `-crf 23 -preset veryfast -b:a 128k`. YouTube captions already worked through the adapter and are unchanged by this work.

- Verified in a real browser (local Worker + R2): both players render the skin control bar and watermark, MP4 plays (`readyState 4`, `currentTime` advancing), HLS plays a visible frame, the `ended` output marks the lesson complete, and rapid lesson switching is clean. Un-muted autoplay was also verified with trusted (real) pointer input: YouTube, MP4 and HLS all start with `muted:false`, and the loading spinner hides only once `currentTime` moves (HLS under a throttled connection shows the spinner instead of the pause icon). When the browser blocks autoplay (no gesture), the spinner becomes a play button after 4 s and one tap starts the lesson with sound.
